# Borrowhood security overview

**Verification.** Supabase Auth owns passwords and email confirmation. Profiles store the protected student/admin role and verification decision. Server helpers require a confirmed BulSU email; verified students also need an approved, submitted profile and photo. Guests and pending/rejected students can browse published content. They cannot post, request or comment. No account revocation feature exists in P1.

**Controlled writes.** Private profile rows are readable only by their owner or a confirmed admin. Browser INSERT/UPDATE/DELETE grants are revoked for profiles, items and requests; comments also deny direct writes. Narrow functions validate the caller, accepted fields and current state. Pending/rejected students can edit only their own name/course/photo and resubmit to Pending. Approved students keep approval after those edits. Only admins review applications, and cannot review themselves. Every function fixes its search path, qualifies tables and has narrow execution grants.

**Public and verified reads.** Public listing-owner summaries expose name, current photo and calculated trust score/badge only. Public Q&A exposes the comment, server time and author name/photo. Hidden/deleted listings and their comments are not public. Full profiles and completed condition-history summaries require verified login. They exclude emails, roles, reviewer notes, private request messages, condition notes and evidence paths. Nonparticipants do not receive private request IDs. Admin status alone grants no extra loan access.

**Requests and agreements.** Verified students request another owner's active item using inclusive future dates within its maximum. Creation and transitions lock the listing before requests. Owner approval reserves dates and atomically declines overlapping Requested rows with a server reason; unaffected dates and history remain. A GiST exclusion constraint prevents overlapping Approved/Handed over reservations. A latest Declined or Cancelled outcome permits another request for that borrower/item; Returned remains a history link. Owner alone approves/declines/confirms handover/return; borrower cancels Requested/Approved only. Rental type/label and meetup details cannot change while an accepted loan is active. Soft deletion is owner-only: pending Requested rows are atomically declined with “Listing removed by owner.” Approved/Handed over loans block deletion before any change. The listing lock serializes deletion with request creation and approval; records/media remain for history. Direct hiding/deletion updates remain guarded.

**Photos.** Buckets are private and enforce JPEG/size limits; the browser resizes uploads. Owned UUID folders and request/event paths prevent foreign assignment. Referenced profile and condition photos cannot be overwritten or deleted through browser APIs. Only owned unused uploads can be cleaned up. Public item/owner/comment avatars have scoped read helpers. Verified profiles expose current approved-student avatars. Request condition evidence remains readable only by verified participants, including after listing removal. This does not expose another pending student's onboarding photo.

**Trust, dates and comments.** Trust is calculated from completed borrows: 100 minus 8 per late return and 15 per damaged return, floored at zero; Minor wear has no penalty. New means no returns; below 70 is Needs attention; five completions and 90+ is Trusted; other completed borrowers are Reliable. Manila dates determine due days and late returns. Overdue is derived after the end date, not stored. The trusted SQL-editor operator may correct request dates under normal constraints for the documented demo; browser callers cannot. Verified comment creation controls author/time and locks the published listing; comment edit/delete is unavailable.

**Defense and verification.** The frontend uses only the Supabase URL and anon/publishable key. There is no service-role key, separate backend, payment processing, app date override or background job. UI guards improve navigation; PostgreSQL grants, RLS, checked functions, locks and constraints enforce security. Local builds/previews do not prove live permissions. Team QA must apply the additive migrations, run the focused rollback suites, test real Storage/API denial and simultaneous approvals, and validate the deployed routes. Deferred photo-security checks remain open until QA records results.
