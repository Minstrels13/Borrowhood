# Borrowhood security overview

**Implementation:** 001–003 cover verification, 010–012 listings, and 020–024 requests/calendar/condition photos and duplicate-request prevention. Phase 4 is local implementation while the team tests Phase 3. Live acceptance and deferred Phase 2 photo-security checks are not marked passed.

**Identity.** Supabase Auth manages passwords and sessions. An Auth trigger rejects outside emails and changes to account email. Signup copies only name/course metadata into a pending student profile; role/status metadata has no authority. Students confirm email, log in, add a photo, then submit. Admins are designated manually in SQL. Preserved accounts missing a profile can create only their own pending profile through the correction function.

**Database boundary.** `profiles` has RLS and no browser INSERT/UPDATE/DELETE grants or policies. A student reads only their own permitted columns; a confirmed admin can read students. Admin notes have no browser column grant. `save_my_profile` accepts only the caller's name/course/owned photo. `submit_my_profile` moves only pending/rejected accounts to pending after confirmation/photo checks. `review_student` requires admin, a pending target and complete onboarding for approval. Profile rows are locked during changes. Approved users keep approval when editing; no revocation or self-review.

**Functions.** Security-definer functions run with empty `search_path`, schema-qualified objects and explicit caller checks. Default PUBLIC execution is revoked; each function explicitly grants only its required browser roles. Public listing-identity/photo helpers allow anon reads; write functions require authenticated callers and check eligibility. `has_confirmed_email`, `is_admin`, and `is_verified` check protected Auth/profile data. The admin queue returns twelve results per page without granting Auth-table access. Every function/policy has a SQL comment.

**Photos.** Private profile/item/condition buckets enforce JPEG-only and 1 MB maximum. Browser compression strips metadata and resizes to an 800-pixel longest edge. UUID folders and new paths prevent foreign uploads/overwrites. Only current avatars of published owners and referenced public item photos gain public reads. Condition uploads belong to the owner/request/event in the appropriate state; recorded photos are participant-only and cannot be deleted. Verified historical participants retain listing/photo/avatar access. Only unused owned uploads can be cleaned up. Database save precedes cleanup; failed saves attempt unused-upload removal. Signed URLs expire after one hour.

**Listings.** Public RLS exposes active, non-deleted items and their photo references. Verified owners can read their own hidden listings. Browser table writes are revoked. `save_item` checks verification and ownership, accepts content fields only, and atomically saves at most three unique, existing, owned photo paths. It cannot change owner, creation time, deletion or visibility. `owner_summary` exposes only ID/name/photo/trust; no course, email or review notes. Until borrowing outcomes exist, trust is New; Phase 5 adds real aggregates.

**Secrets and UI.** Only project URL/anon key reach the browser; `.env` is ignored. UI route guards guide users, while grants/RLS/functions enforce access even with direct API requests. Email confirmation must be enabled in Supabase. The signup form opens the confirmed community rules in a native dialog; signup stores its version in Auth metadata.

**Requests.** RLS permits verified participants only; direct browser INSERT/UPDATE/DELETE and sequence access are revoked. The creation function checks verification, non-ownership, active listing, inclusive future dates and per-listing maximum. Transitions lock the listing before the request, recheck actor/state and record server timestamps once. Owner approves/declines/hands over/returns; borrower cancels requested/approved only. A GiST exclusion constraint prevents overlapping approved/handed-over dates, including concurrent approvals. Approval atomically declines overlapping pending requests with a server reason; unrelated dates and history remain unchanged. Requested dates do not reserve. An insert guard locks the item and permits a repeat borrower/item request only when the latest request is declined; cancelled/returned requests remain history links. Public availability returns dates or a boolean only. Private detail returns participant name/course/photo without email/review fields. The paginated per-item list verifies item ownership and exposes only participant request data and borrower name/photo. No special admin access to loans.

**Dates/history.** Dates and overdue use Asia/Manila: return by end_date, overdue next local day, never a stored status. Requested/approved/handed-over requests block hiding/soft deletion. History persists. Browser functions accept no date edits; the trusted dashboard postgres role may correct dates under ordinary constraints, as documented for the overdue demo. No app override, trigger bypass or background job exists. Full profiles/history and trust aggregates remain Phase 5.

**Evidence.** Focused rollback SQL checks use existing real team records. Manual steps are in `manual-tests.md` and the phase setup files; `pnpm check:requests` checks Manila/date/role-state boundaries. Local checks do not prove live RLS/Storage or concurrency. Functions follow [Supabase's fixed-search-path guidance](https://supabase.com/docs/guides/database/functions); booking exclusion follows [PostgreSQL range constraints](https://www.postgresql.org/docs/current/rangetypes.html).
